# Shared Build and Packaged E2E design

Draft for owner agreement, 7 October 2026. This proposal moves orchestration and evidence authentication into mod-base. It does not authorize implementation, a release, consumer changes or GitHub settings changes.

Use one execution trust model: protected default-branch controllers, with candidate execution confined to disposable credentialless accounts. Preserve Quick Skin's isolated target builds, one Build bundle per PR generation, isolated runtime lanes, draft deferral, batches and authenticated identical-tree reuse. Preserve Block Pops' protected policy, independent sealing and validation, App-sourced required statuses, exact job graphs and SHA-bound controller upgrades. Quick Skin needs a deliberate governance upgrade to adopt this model; copying its current workflows would not preserve Block Pops' protections.

## Trust model and protection changes

Both mods should run PR orchestration from protected `master` on `pull_request_target`. `github.sha` identifies the controller, not the candidate. Candidate Python, tests, Gradle, harness generation, Minecraft and dependency installation run only inside the disposable account. A separate protected validator checks frozen exports before any upload. Small fresh jobs publish statuses or dispatch advisory work.

Quick Skin's current candidate-owned workflows and token-bearing helper execution cannot coexist with Block Pops' boundary. Those parts are replaced. Its performance topology can coexist with the boundary because runner isolation, bundle authentication and governance are independent concerns.

Block Pops retains all of the following: protected-path parity and forbidden-path rules; exact ordered merge parents and tree identity; matrix enrollment and scope restrictions; loader-bootstrap seals; wrapper and dependency policy; independent compiler observations and JDK probes; exact production/harness separation; tracked-source immutability; credentialless execution; process termination and account locking; sealed exports and second-account revalidation; exact attempt/job/artifact authentication; statuses-only App credentials; current-head owner approval, revocation and writer rechecks. Release synchronization and restricted transitions keep their existing admission rules. No ordinary PR or batch gains a new route around them.

The kit implements the common mechanism. Each mod owns its protected-path inventory, release routing and authority configuration. Quick Skin should adopt an equivalent exact-head owner-approved controller-upgrade route and statuses-only App authority before making shared gates authoritative. This strengthens its current zero-required-review governance and changes the expected App source, while preserving the displayed required names. Until that prerequisite is complete, its legacy workflow remains authoritative; a shadow run cannot substitute for it.

There are two explicit policy changes to review, not tests to delete when inconvenient:

1. Block Pops' workflow security test currently asserts global Gradle serialization. Replace that assertion with isolated hosted runners, private accounts/checkouts/cache copies, serial Gradle within each worker, process quiescence and per-PR workflow locks. Global serialization is unnecessary once workers do not share a JVM or filesystem. All task/report/packaging assertions remain.
2. The kit's predecessor-reader test currently assumes every newly written document, including a new kind, is readable by the previous release. Correct its scope as described under schema evolution. Keep strict rejection and existing compatibility regressions; explicitly test unsupported kinds failing closed.

Quick Skin deliberately has `org.gradle.dependency.verification=off`, documented in [DEPENDENCY-SECURITY.md](https://github.com/The-Plum-Team/Quick-Skin-Mod/blob/c0cdc01ab20f1eac663c628011520c76fc7e3d7a/DEPENDENCY-SECURITY.md). That is incompatible with treating all external executable dependencies as hash-enforced inputs. The proposed common gate requires strict external dependency verification. Quick Skin needs a separately reviewed lock/enforcement change and full-target validation before cutover; do not silently reproduce the exemption or generate new accepted hashes during CI. Existing narrow exceptions for locally generated artifacts remain mod-owned and must prohibit those namespaces from remote repositories. Block Pops' strict mode is never relaxed.

Introduce `BUILD_ADAPTER_API = 1` independently of Pages `ADAPTER_API = 1`. Neither protocol silently gains candidate execution authority. A protected Build/E2E configuration file at `scripts/ci/mod-base-build.json` supplies fixed adapter paths and repository policy; the profile activation manifest lives under `site/`. Both paths already lie within Block Pops' allowed controller roots. Every adapter import dependency must also be protected. Neither file contains a second version/scenario inventory. Their precise versioned schemas are part of the first protocol PR, not unreviewed optional keys inserted into existing v1 config.

The protected adapter has closed hooks for inventory/plan derivation, native target verification, aggregate build verification, runtime-plan derivation and native result verification. Trusted parsing reads bounded candidate Git blobs as data using protected parsers. It never imports a candidate matrix/scenario module into the controller. Build/runtime command hooks execute through a fixed dispatcher inside the candidate account. Protected verifiers run against frozen bytes under the separate validation account, with no token. Hooks cannot return shell programs, runner labels, permissions or arbitrary upload paths.

Native JSON reports/manifests also get strict bounded decoding and a mod-owned closed schema before domain verification. A strict outer envelope alone cannot fix a duplicate-key or unknown-field ambiguity inside an inventoried native file. This explicitly strengthens Quick Skin's current plain `json.loads` readers while retaining all their hash, inventory and packaging checks. Keep native timeouts and profile bounds until a separately reviewed change justifies another value; a generic worker default cannot silently alter them.

Plans contain opaque target/lane IDs, expected production/harness/SBOM outputs, toolchain requirements and native validation contracts. They are derived from the release inventory and scenario contract once, then independently re-derived at fan-in and gate admission. Every supported target remains required. Quick Skin's authenticated feature-selection extension stays domain policy: it may reduce authored action/capture scope only with its existing complete-baseline proofs. Block Pops receives no selective-scenario exception. Unknown or unavailable selection proof chooses full profiles; malformed authenticated proof or an API failure stops admission.

Use separate kit workflows such as `build.yml`, `select-build.yml` and `packaged-e2e.yml`. Callers compose them at one literal SHA. E2E does not call the kit's Build reusable workflow from inside another kit workflow: explicit kit self-references outside the canary remain forbidden. This also avoids depending on unverified nested relative-call resolution. Within a kit job, local composites are used only from the verified kit checkout.

For a standalone E2E dispatch, the managed caller first selects an existing authenticated Build or calls the same Build reusable workflow, then invokes E2E. Bind a request identity to the protected subject, controller/pin, profile and requesting E2E run/attempt; cross-run recovery also binds a unique request nonce. Dispatch code only from the protected default ref. If that ref/controller advances, reject or restart under a new identity instead of substituting a newer Build. For a PR, its compile branch is forbidden: it waits for the separate exact Build producer. This avoids introducing a second compiler implementation or an unpinned workflow dispatch route. Release rehearsals and reproducible rebuilds keep their explicit full-run semantics; they are not reclassified as ordinary CI reuse.

## Identity and execution boundaries

Every plan, partition, aggregate and gate receipt binds the following distinct identities:

- Repository, PR number and source repository; head SHA and branch; base SHA and branch.
- Protected controller SHA and workflow path/ref; executing kit repository/SHA/version and tree digest.
- Exact tested merge commit, its ordered parents and complete tree. For protected push/standalone execution, the tested commit/tree instead name that exact protected subject.
- Controller policy digest, graph protocol/version, inventory blob/hash, scenario contract hash, build plan hash and runtime selection/profile hash.
- Producer run ID, exact attempt, artifact IDs/digests/sizes and upload windows. E2E also names its owning Build run/attempt and bundle artifact.

The run API's `head_sha`, a caller input, a candidate self-report or an artifact name alone cannot establish this tuple. Read PR and Git objects independently; recheck source/head/base/draft/controller freshness before executing and before publishing a success. Build and E2E compare the entire admitted tuple. If the base moves and GitHub regenerates the test merge, old head-only evidence does not qualify.

Every new callee job gets a common **Build controller prologue** before running kit Python: validate exact inputs; checkout the protected mod at the authenticated controller SHA and kit at the verified SHA; require clean trees; reject inherited `GIT_*`; bind caller path/event/controller identity; recompute kit-digest-v1 and compare the literal. This is additive. Existing Pages prologues remain unchanged, including their exact `pages.yml` workflow-ref guard.

An independent caller-owned shell guard authenticates `referenced_workflows`, the protected pin and kit `main` reachability before entering privileged kit code. The callee cannot be its own impostor defense. Canary validation must establish the API behavior for skipped calls and running callees; never assume an unavailable reference is proof. Before a candidate future kit pin is staged, protected bootstrap code checks its immutable release tag and ancestry. Candidate policy remains untrusted even if that pin is valid.

The executing protected pin and an approved candidate's future pin have different roles. During a controller upgrade, only the old protected implementation authorizes/plans/seals the PR; the proposed new kit may be staged in the candidate account for tests. Candidate workflow references never choose privileged code. A new adapter/matrix schema unsupported by old protected parsing needs a compatibility-first rollout.

### Worker lifecycle

1. A clean hosted runner performs protected authentication and tool installation. Checkouts disable persisted credentials. Cache restoration is controlled by protected policy.
2. Protected code copies the candidate and verified overlay into a private boundary, allocates a fresh no-sudo UID, and builds an explicit environment. It excludes GitHub command files, runtime/cache/artifact credentials, token variables, user sites and protected runner/action directories. Candidate package installation and `.pth` files stay in that account. Protected Python uses safe fixed import paths and no candidate working directory.
3. The worker runs one target's reviewed serial Gradle plan or one runtime lane. It uses a private cache copy and fresh game workspace. Normal completion, failure, cancellation and timeout all require termination/reaping; a surviving candidate process forbids export/upload.
4. Protected code kills and locks the UID, verifies complete tracked-source identity and allowed generated roots, then freezes bounded exports behind ownership the candidate cannot change. It rejects symlinks, hard links, special files and traversal.
5. A second disposable no-sudo UID runs protected verification, independent from candidate code and credentials. Validate native compiler/report/JAR/scenario/image assertions plus the kit envelope. Kill/lock that UID and freeze its receipt.
6. Only then may pinned upload and cache-save actions consume the sealed outputs with their runtime credentials. Earlier protected read-only cache restoration is permitted, with its credentials/files inaccessible to both disposable UIDs. A fresh final evaluator checks owner/attempt/graph/artifact metadata and the sealed receipt. A distinct fresh App writer reauthorizes the live PR and owner approval before minting a statuses-only token.

An empty environment alone is insufficient isolation. Artifact/cache runtime credentials can exist in the host runner independently of `GITHUB_TOKEN`; `permissions: {}` does not remove them. Preserve Block Pops' filesystem/process boundary. This design adopts that boundary; it does not claim a separate Unix account is a VM or eliminates kernel vulnerabilities. General self-hosted persistent runners are unsupported in the initial profile.

Every new caller/callee has top-level `permissions: {}` and explicit minimum job grants. No kit callee declares secrets or concurrency. No `secrets: inherit`. The status writer is a fresh caller-owned native job with fixed reviewed App secret/environment names, not a secret-bearing kit callee or data-selected wrapper. Candidate execution receives no token. Domain adapter hooks never run with `actions: write`, `pages: write` or `id-token: write`; status credentials are minted only in the final writer. Event/input values enter shell commands through `env:` with exact validation. Actions use full commit SHAs with version comments; Python installations use committed hashes and binary-only wheels. Kit runtime code keeps Python 3.11–3.13 and stdlib plus the existing lazy hash-locked imaging dependency. [GitHub's reusable workflow permission rules](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations) also prohibit a callee from elevating its caller's grant.

## Scheduling and evidence behavior

### Concurrency and isolated fan-out

Managed callers own separate `build-gate-<workflow>-<PR>` and `packaged-e2e-<PR>` groups. Protected non-PR requests use distinct authenticated workflow/subject/request keys; a current-default generation may coalesce/cancel its obsolete predecessor, while independent manual requests never cancel one another. New source generations cancel obsolete work within that PR; separate PRs do not share a compilation lock. App result writers may have a short per-PR non-cancelling lock, never held during Build, Minecraft or long polling. Pages/release locks retain their independent purposes.

Build derives one runner per Minecraft target. Within a runner, loader tasks and any compiler invocations remain serial. Block Pops currently supports full/legacy plans or one `--artifact-node`, not an arbitrary target-subset manifest. Its adapter serially runs existing lane plans for all loaders of the protected target and preserves each lane bundle/report; it never combines Forge and NeoForge remapping in one JVM. Native fan-in verifies the exact full union, retaining every lane's command, JDK observations, task set/outcome/class destinations, build identity and manifest verification. A new native target-scope format would need its own explicit schema/validator upgrade. Success booleans do not replace those observations. Generic suite execution also preserves each mod's discovery/count/failure rules, including Quick Skin's deliberate whole-class `setUpClass` skip semantics.

Runtime derives one runner per required version/loader lane. `fail-fast: false` preserves sibling diagnostics; aggregation and the gate still require every planned lane. No default author-maintained `max-parallel` ceiling limits either wave. The validated bounded plan and account allowance determine actual width. Runner capacity can queue jobs; it cannot reduce coverage. An optional future capacity profile may delay work but cannot omit it or count a skipped worker as passing.

### Build bundle handoff

Build uploads attempt-specific target partitions, independently validates and assembles their exact union, and seals one complete staged bundle only after every compilation and policy leg succeeds. E2E selects the newest matching Build generation/run and exact attempt **before** checking success; querying the latest successful run is forbidden. It waits for that producer for the exact PR tuple and authenticates its completed graph and successful sealing/upload steps, not just artifact existence. Bounded polling retains Quick Skin's existing maximum of 5400 seconds; a timeout fails visibly and asks for a complete rerun. Account queueing may consume this budget. A later recovery wake must reauthenticate the whole source rather than revive a stale run.

Every transfer, including same-run partitions, uses immutable numeric artifact IDs. Preserve ID, digest, owner run/attempt, expiry, size, workflow identity, exact graph and upload window through a canonical descriptor; do not drop the digest after selection. Download with the kit's bounded authenticated transport and safe extractor, then independently reverify native staged production/harness/SBOM bytes against the tested merge and full plan. A candidate manifest cannot choose a destination or reinterpret a target.

Quick Skin currently uses numeric IDs across runs and checks native staged hashes, but its selector only checks the successful gate, not the whole Build graph; it omits upload-window checks and drops the authenticated digest from workflow outputs. Same-run compilation assembly uses artifact-name patterns. The kit must strengthen both transports, preserving native verification. Block Pops' native manifest/report/archival checks remain in force.

Introduce separate build artifact names/kinds and limits in kit grammar/limits. Do not enlarge existing screenshot or Pages ZIP budgets. Preserve Quick Skin's current 512 MiB compressed full-bundle admission cap for its profile. Preserve Block Pops' sandbox bounds (at most 16 exports; each exported tree at most 10,000 files, 20,000 entries, 1 GiB/file and 2 GiB expanded), native JAR bounds (256 MiB, 8192 entries and its existing nested/expanded limits), and runtime/fan-in bounds. Those include runtime exports of at most 512 files/256 MiB per profile, 4 MiB reports, 16 MiB logs and 32 MiB PNGs, plus the native 512 MiB fan-in budget. A transport's compressed and expanded caps are specified independently; exceeding a cap fails and requires a separately justified format/storage change. The assembled logical export keeps its original whole-tree limit across all target partitions; partition count cannot multiply it. Any new cross-export aggregate budget is an explicit additional protection, not misrepresented as an old global cap.

Retain staged source bundles and raw runtime artifacts for seven days for ordinary reuse, sealed small tested/reuse records for 90 days, and transient target partitions for one day. This changes Block Pops' ordinary source-artifact retention explicitly and needs storage measurement; it does not extend evidence validity or resurrect expired bytes. Pages' existing one-day handoffs, anchors/baselines and rotation policy remain. New build artifacts are excluded from Pages rotation and legacy names remain untouched.

### Drafts and batches

Use `opened`, `synchronize`, `reopened`, `ready_for_review` and `converted_to_draft`, plus existing protected admission/approval triggers. Before candidate work, authenticate current draft state. Drafts allocate only a small protected deferral/report job with distinct names; no compiler/runtime worker, staged bundle, tested seal or success under a required context is emitted. A readiness event starts fresh gates even if the head SHA is unchanged. Deferred attempts are ineligible bundle producers. Converting a live PR to draft cancels candidate work and the protected writer invalidates prior authority for that head; marking it ready cannot revive a previous green status.

Move the generic batch constructor and membership verifier into kit Python. Preserve Quick Skin's maximum of 50 members. Batch manifests bind base SHA, ordered members, each source repository/head/tree, patch inventory and resulting tree. A privileged automation writer uses protected `git commit-tree` with a fixed bot identity and sanitized Git configuration/environment, producing one squash commit per member without hooks/filters/external drivers. Revalidate before writing, including the original tool's empty branch lease, conflict/no-op rejection and exact-head settlement checks. Require same-repository members and exact live membership; conflicts, moved heads, unsafe patches, unknown paths or malformed manifests stop construction. The resulting `batch/*` PR runs the complete unchanged target/loader gates once and is itself subject to source freshness and App admission.

Block Pops batches initially accept only ordinary permitted changes. Protected controller upgrades, restricted transitions, kit bumps and matrix changes never hide inside a batch. Quick Skin's current rule that kit bumps land through batches changes under the common governance: they take the explicit controller-upgrade route with owner approval of the final SHA. Batch settlement checks the merged batch's complete provenance before closing members; design approval does not authorize creating/pushing/merging a batch or closing anyone's PR.

### Post-merge reuse

Reuse authenticates the actual merged PR and both original gates independently. Independently verify the original tested merge's ordered parents, then prove its complete tree equals the final merged tree, not merely a patch or branch name. Final merge/squash/rebase parents may differ; this never relaxes the original test-merge parent check. Require identical protected execution policy, executing kit pin, graph protocol, inventory, scenario contract and selection semantics. The controller SHA will change after an ordinary merge; compare a closed protected-policy digest derived by trusted code, while retaining the original controller SHA as provenance. Unknown policy ownership chooses a full run. Any control-plane/kit upgrade changes this digest and runs full gates after merge.

The original exact attempt must have its whole successful expected graph, immutable tested seals and still-available Build/runtime artifacts. Preserve Quick Skin's coupling: Build reuse requires eligible original runtime reuse too. If either original proof is genuinely unavailable, choose a fresh coherent Build/E2E generation rather than a mixed reused/new source set. Independent consumers reauthenticate the source; references retain tested commit/run/attempt/artifact/JAR identity and separate covered merge identity. Block Pops' embedded original `META-INF/blockpops-build.json` commit/tree is never rewritten to pretend the reused JAR was built after merge. References do not chain, renew artifact retention or claim that Minecraft ran in the lightweight reuse job. Reuse is an explicitly admitted graph mode with a protected successful verifier and defined skipped workers. Release rebuild/reproducibility and explicit full-recovery requests bypass it.

Quick Skin's Pages/feature coverage, curation, review, compatibility, target-status and attestation consumers currently encode `pull_request` and conflate some tested/controller identities. They need coordinated versioned readers for the new generic reference; reusing the current JSON unchanged is unsafe. Block Pops' release-sync attestation remains a separate mode with its exact source/target parent and matrix-preservation requirements.

| Failure or missing proof | Required behavior |
| --- | --- |
| Draft/deferred Build for a now-ready PR | Ignore it as a producer; wait for a fresh ready generation, bounded by the wait limit. |
| No Build, pending Build, or polling deadline | No Minecraft admission and no green gate. Wait boundedly; then fail closed. Recovery reruns Build and E2E for current source. |
| Latest Build failed/cancelled or tuple/base/merge moved | Reject. Never use an older successful head-only Build. |
| PR Build bundle missing/expired | Fail closed; rerun Build. PR E2E never compiles independently. |
| Standalone or post-merge evidence genuinely unavailable/expired | Select a fresh complete Build plus E2E run through the same shared workflows. Re-evaluate both gates; do not manufacture a reuse success. |
| Malformed/ambiguous metadata, digest/hash/graph mismatch, unsafe archive, unknown scope | Fatal visible failure. Never downgrade authenticated corruption to an optimization miss. |
| GitHub API failure | Bounded classified retry, then visible failure. Never treat it as absence or permission to use old proof. |
| Source attempt still pending during reuse admission | No reuse and no success. Wait boundedly or stop; do not race a new full run against unproven original authority. |
| Failed-jobs-only rerun mixes attempts | Reject incomplete attempt graph/receipts; recovery is rerun all jobs. No cross-attempt mosaic. GitHub lists a carried-over job under the new attempt with a new id: a job that started before the attempt's `run_started_at` is refused as one (K7 canary, v1.1.2). |
| Source artifacts disappear after selection | Recheck/reject before consumption or App success. A new full recovery may start independently; the failed consumer cannot pass. |
| Missing batch members or required lanes/obligations | Reject. Authenticated selected action/capture scope may pass the ordinary gate only with every required lane and every selected obligation; it cannot serve as full-baseline/release/full-scope proof. Unknown optional selection chooses full scope before execution. |
| Advisory Pages/AI/wake failure | Preserve deterministic gate semantics and previous public site. No advisory status replaces required evidence. |

## Stable contexts and exact graphs

Keep public required context strings stable across kit bumps. Block Pops keeps its existing App and both `Trusted PR / ...` names. No substring/suffix matching, acceptance of unexpected jobs, duplicate collapse or observed-jobs-driven graph selection.

A routine kit patch/minor bump keeps that graph contract and public context strings unchanged. A graph change gets its own protocol/version decision and compatibility-first consumer upgrade. Artifact owners remain bound to the producing controller/pin/graph; old artifacts are not validated using whichever pin is current. ## Risks and unresolved questions

1. **GitHub event-policy readiness.** Current primary documentation says default public-repository `pull_request_target` policy enforcement starts November 2, 2026. Read-only Actions-policy APIs returned no explicit applicable/inherited policies for either mod. That does not prove the default evaluation policy is absent. An owner must verify applicability and authorize any required policy before rollout; no setting was changed. [GitHub's current policy guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).
2. **Quick Skin governance and dependency policy.** The proposed common model strengthens both. Its documented batch-only kit-bump route and governance reconciler need coordinated updates. Whether the owner accepts those changes is a design decision, not an implementation assumption hidden in a pin bump.
3. **Kernel and runner assumptions.** Block Pops' account boundary is the reviewed starting point. A port can regress directory permissions, import isolation, process quiescence or caching. Linux adversarial tests and the real canary are required. Stronger VM/container isolation can be a later reviewed replacement; it cannot be claimed here.
4. **Platform API identity.** Reusable-workflow prefixes, skipped identity anchors, attempts, App/check collisions and status placement need live canary evidence. Current kit docs already acknowledge limits to observations inside a callee. A fixture cannot prove undocumented API behavior.
5. **Bounds and artifact growth.** Complete shared bundles and receipts may approach current limits as matrices grow. Their actual sizes were not downloaded/measured here. Measure before choosing final transport partitioning; do not expand a bound because a pipeline fails. Retaining Block Pops source artifacts for seven days increases storage and requires measurement.
6. **Compatibility closure.** Quick Skin's selected-scope and original-controller/tested-merge assumptions span many consumers. Block Pops' App evaluator, release attestations, visual review and adapter fix exact graphs. The first implementation must enumerate all callers with source searches and fixture parity; unsupported historical modes remain on legacy routes until explicitly supported.
7. **Schema tests versus written policy.** The predecessor-reader assertion and strict unknown-key rules cannot justify arbitrary optional additions/new kinds. The explicit compatibility-ledger amendment needs approval and version decisions before any new schema is shipped.
8. **Release determinism and commit-derived metadata.** Tree equality alone cannot authorize release reuse when build metadata depends on commit/event. Require unchanged build semantics and retain original tested identity. Releases continue full rehearsals and reproducibility builds. Confirm each adapter's commit-derived fields during conformance.
9. **Capacity and wait limits.** Account quotas, cache warmth and long policy suites can still dominate. The 5400s Build wait fails closed under excessive queueing. Recovery scheduling may later improve cost, but must retain exact source freshness and cannot report green while waiting.
10. **Missing specification source.** Kit docs cite `SPEC` sections, but no tracked/local SPEC document was found. This review used maintained docs, validators and tests. Recover or retire those external references as documentation work; do not claim the absent SPEC was verified.
11. **Previously green App status during outage.** A status API has no synchronous revocation guarantee when a writer fails after draft/base/approval changes or artifacts expire. Independent reconciliation reduces this window but cannot prove instant fail-closed merging. Preserve Block Pops' owner procedure and require a fresh protected live-evidence/approval check immediately before any merge, including batch settlement. For strict enforcement against other authorized mergers, owner-authorized restriction to a protected merger that repeats this admission is a prerequisite; a statuses-only App must not be broadened into a merge token. Whether to enforce that merge route in Quick Skin is an unresolved governance decision. The new evaluator itself always fails closed; an old stored status is not new proof.
12. **Existing native validation debt.** Block Pops' mod-base adoption ADR records a matrix tree-entry mode limitation in the adapter's `ctx.read_blob` path. This review did not resolve it. Preserve all present checks, add a bounded mode-authenticated blob interface if needed through its own versioned change, and do not describe existing validation as stronger than it is.

Source inspection and live API measurements were completed; sandbox correctness, build reproducibility and runtime outcomes were not reproduced locally. No Gradle or Minecraft command ran. The consumers' POSIX-only Python policy suites could not run on this Windows host; Linux UID/no-follow/sealing tests, actionlint/shellcheck, real workflow canaries and the kit's Python 3.11/3.13 implementation suites are future implementation/release requirements. No implementation code, managed file, GitHub setting, commit, push or PR was changed in this session.

Owner agreement is requested on this unified protected model, its explicit governance/dependency/compatibility changes, and the staged rollout. Implementation stops here until that agreement.
